# Role-gated accounts management with hardcoded staff sign-up

Four requirements land together: the Sign Up form drops its role selector and hardcodes `staff`; `AuthContext` gains a user registry exposed to consumers with `updateUserRole`, `toggleUserActive`, and `deleteUser`; Settings gains an Accounts Management card visible only to Admin; and `StatusBadge` gains `Active`/`Inactive` tones. The approach is entirely in-memory (no backend), consistent with the existing auth stub.

Watch for: (1) **confirmed** — `login()` does not check `found.active`, so a deactivated account can still sign in. (2) **confirmed** — `deleteUser()` has no guard against deleting the currently logged-in user; an admin can delete their own account, leaving the session referencing a ghost user. (3) **confirmed** — the `active` flag is stored but never enforced at login, making `toggleUserActive` cosmetic rather than functional.

**Verdict**: NEEDS_CHANGES

---

## High-level view

The Sign Up form passes the literal string `'staff'` into `register()` — no role state, no role UI. The `INITIAL_USERS` seed includes `admin`/`admin123` with `active: true`, and newly registered users also get `active: true`.

The Accounts Management card in Settings is wrapped in `{isAdmin && (…)}`, using `isAdmin` from `usePermissions()` which derives from the live session — a non-admin cannot reach the section even by direct URL navigation. The DataTable shows username, role, and status badge; the Change Role and Delete Account modals follow the existing supplier-modal pattern.

The `active` flag is visually correct but carries no enforcement weight. `login()` checks the password and immediately calls `setUser()` — `found.active` is never read. A deactivated account can sign in without restriction. `deleteUser()` has no guard against `username === user.username` despite the JSDoc comment saying it must not delete the currently logged-in user.

<summary>Issues (3)</summary>

1. **Deactivated accounts can still log in** — `login()` in `AuthContext.jsx` never reads `found.active`. Add a check after the password test: `if (!found.active) return { ok: false, message: 'Account is deactivated.' };`

2. **Admin can delete their own account** — `deleteUser()` has no guard against `username === user.username`. The comment in the source says "must not delete the currently logged-in user" but the implementation does not enforce it. Add a guard in `deleteUser` (the `user` variable is already in scope inside `AuthProvider`) or in `handleDeleteAccountConfirm` in Settings.

3. **`toggleUserActive` is cosmetic** — because `login()` ignores `active`, deactivating an account has no real effect. Resolved by fixing finding #1.

</details>

<details>
<summary>Details</summary>

### Active flag ignored at login

`login()` finds a matching user, checks the password, and immediately calls `setUser()` — `found.active` is never read. The `toggleUserActive` action correctly flips the flag in `registeredUsers`, and the DataTable reflects the new value, but nothing prevents the deactivated user from signing in again. The fix is a single guard between the password check and `setUser`:

```js
if (!found.active) return { ok: false, message: 'Account is deactivated.' };
```

Without it, the deactivation feature is a visual affordance with no security effect.

### Self-deletion path

The JSDoc on `deleteUser` says "Must not delete the currently logged-in user", but the implementation is:

```js
deleteUser: (username) => {
  setRegisteredUsers((prev) =>
    prev.filter((u) => u.username.toLowerCase() !== username.toLowerCase())
  );
},
```

No comparison against `user.username`. An admin who clicks Delete on their own row removes themselves from `registeredUsers` while the session object (`user`) remains set. Navigations that read `user.role` will still work for the remainder of the session, but re-login after logout fails because the account no longer exists. The `user` variable is already in scope inside `AuthProvider`'s closure, so the guard can be added directly inside `deleteUser` without any props change.

</details>
