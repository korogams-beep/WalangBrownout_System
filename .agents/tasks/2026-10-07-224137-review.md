# Role-locked Sign-up, Admin Account Seed, and Accounts Management

Self-registration is now hardcoded to the `staff` role — the role selector is gone from the Sign Up form and `register()` is called with the literal string `'staff'`. Three account-management actions (`updateUserRole`, `toggleUserActive`, `deleteUser`) were added to `AuthContext`, backed by an in-memory `registeredUsers` list that is now exposed in the context value. A new Accounts Management card in Settings surfaces this list as a DataTable with role-change and delete modals, visible only when `isAdmin` is true. `StatusBadge` received `Active`/`Inactive` tone entries to support the status column.

Watch for: **self-deletion is not guarded** (confirmed) — an Admin can delete their own account from the table, leaving the app in a broken session state. **Active flag is not checked at login** (confirmed) — a deactivated account can still sign in successfully.

**Verdict**: NEEDS_CHANGES

---

## High-level view

The role selector removal is complete and correct. `Login.jsx` passes the literal `'staff'` to `register()`, there is no role-related state left in the component, and `AuthContext.register()` accepts the value without issue.

The default Admin seed (`admin` / `admin123`, `active: true`) was already present in `INITIAL_USERS` before this change; the change adds `active: true` to all three seed rows, which is correct and consistent.

`registeredUsers` is properly threaded through the context — exposed in the `value` memo, destructured in `Settings.jsx`, and used directly as the `rows` prop of the `DataTable`. The three new actions follow the same `setRegisteredUsers` functional-update pattern used by the existing `register` action.

The Accounts Management card is gated identically to Supplier Management (`{isAdmin && (…)}`), uses the same modal overlay/box markup, and reuses `.supplierActions` / `.supplierActionBtn` CSS classes for the action buttons — consistent with the existing component conventions. `.accountsCard` was added to the stylesheet with the same `margin-bottom: 18px` as `.supplierCard`.

Two behavioral gaps survive: an Admin can delete themselves (session becomes a logged-in ghost with no matching registry entry), and `login()` never checks the `active` flag, so deactivating an account has no enforcement at the authentication boundary.

<summary>Issues (2)</summary>

1. **Self-deletion not guarded** — `deleteUser` in `AuthContext` does not prevent deleting the currently logged-in user, and the delete button in Settings renders for every row including the current user's own account. After deletion the session `user` object remains set (pointing to a now-removed registry entry), breaking any logic that re-looks up the user by username. Add a guard in `deleteUser` (or in the Settings handler) that compares `username` against `user?.username` and rejects the operation, or disable the delete button when `acct.username === user?.username`.

2. **Deactivated accounts can still log in** — `login()` in `AuthContext` validates username and password but never reads the `active` field. An admin who deactivates a staff account via the new toggle expects that account to be locked out, but the user can still sign in successfully. Add an `if (!found.active) return { ok: false, message: 'Account is deactivated.' }` check in `login()` after the password validation.

</details>

### Self-deletion creates a ghost session

`deleteUser` filters the target out of `registeredUsers` unconditionally:

```js
deleteUser: (username) => {
  setRegisteredUsers((prev) =>
    prev.filter((u) => u.username.toLowerCase() !== username.toLowerCase())
  );
},
```

There is no comparison against `user?.username`. In Settings, the Actions column renders the Delete button for every row in `registeredUsers`, including the row for the currently signed-in admin. Clicking Delete on one's own row removes the entry from the registry while leaving the `user` session state intact. From that point forward, the session carries a username that does not exist in `registeredUsers`, which would break any future lookup (e.g., role checks that re-query the registry, or a Module 2 sync). The fix belongs either in `deleteUser` itself — `if (username.toLowerCase() === get current user username) return;` — or as a conditional `disabled` prop on the delete button for the row where `acct.username === user?.username`. **Confirmed** — traced through `AuthContext.jsx` and `Settings.jsx`.

### Active flag is not enforced at login

`login()` in `AuthContext` checks username existence and password match, then sets the session:

```js
if (!found) return { ok: false, message: 'Username not found.' };
if (found.password !== password) return { ok: false, message: 'Incorrect password.' };
setUser({ username: found.username, role: found.role, loginTime: new Date().toISOString() });
return { ok: true, role: found.role };
```

`found.active` is never read. The Deactivate button in Settings changes the flag in the registry, but because `login()` ignores it, the "deactivated" account can immediately sign in. This renders the deactivate feature non-functional as a security control. **Confirmed** — `login()` has no `active` guard anywhere in `AuthContext.jsx`.
